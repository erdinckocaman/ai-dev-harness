# The kit — agent-first scripts for Spring Boot microservices

A small set of shell scripts and conventions for working on several Spring Boot microservices
that share one shape, together with an AI coding agent (Claude Code, Codex, opencode, …).

The kit is one part of the ai-dev-harness **workspace**, next to `standards/`, `hooks/` and
`projects/`. It does not live in any service repository. The service repositories stay exactly
as the team keeps them.

## The four ideas

1. **The workspace sits beside the code, not inside it.** No AI-tool file, suite or script is
   committed to a service repository ([`WORKFLOW.md`](WORKFLOW.md) invariant 2,
   [ADR-0001](../docs/adr/0001-workspace-beside-the-code.md)).
2. **One kit, not a copied template.** Each service gets a project folder with a small
   `service.env`, and every script takes `--project <name>`
   ([ADR-0002](../docs/adr/0002-one-kit-not-a-copied-template.md)).
3. **Scripts that do not lie.** Each script exists because a plain command reported success
   when something was wrong:
   - `run-local.sh` — with `spring-boot-devtools`, Maven prints `BUILD SUCCESS` even when the
     Spring context fails to start. The script reads the run output and exits `1`. It also
     stops the full script → Maven → JVM chain, and never kills a process that is not the
     service.
   - `mvn-test.sh` — surefire prints `Tests run: 0` for `@Nested`-only classes, and a method
     filter silently drops nested classes. The script reads the XML reports and fails when no
     test ran.
   - `set-version.sh` — sets one version in every `pom.xml` and the Helm `appVersion`, then
     verifies that no stale reference is left.
   - `run-suite.sh` — runs [hurl](https://hurl.dev) acceptance suites with **gates**: a block
     for an endpoint that the target has not shipped yet is skipped by version; a block that
     needs a special arrangement of the target runs only when you declare it.
4. **Acceptance tests as plain text.** hurl files replace a Postman collection: they diff
   well, an agent can read and update them in the same change as the endpoint, and one binary
   runs them. See [`acceptance-tests/`](acceptance-tests/).

## Layout

```
kit/
  README.md                  # this file
  WORKFLOW.md                # the agent workflow: two invariants and the workspace-first loop
  regenerating-codebase.md   # how an agent regenerates a project's CODEBASE.md
  scripts/                   # run-local, mvn-test, set-version, run-suite, check (see scripts/README.md)
  checks/                    # the Maven module behind check.sh: ArchUnit rules, tool versions
  acceptance-tests/          # hurl conventions: running and gating, assertion house style
  examples/projects/sample-service/   # a complete service project to copy
```

The scripts work on the project folders under `projects/` of the harness:

```
ai-dev-harness/
  kit/                       # this folder
  projects/
    orders-service/          # one folder per service
      AGENTS.md              # what is true of this service only; points at the kit
      CLAUDE.md              # @AGENTS.md
      service.env            # the values the scripts read
      CODEBASE.md            # structural map, regenerated by the agent
      acceptance-tests/      # suites/*.hurl, environments/*.env
```

## Quick start

Create the project folder with the `new-project` skill (`/new-project <repository path>`) at
the workspace root, then:

```bash
cd projects/orders-service
../../kit/scripts/set-version.sh               # print the current version
../../kit/scripts/run-local.sh --env ~/.ms-kit/local.env
../../kit/scripts/run-suite.sh --env local --app-version 1.2.0
../../kit/scripts/run-local.sh --stop
```

Inside a project folder the scripts find the project themselves; from anywhere else, pass
`--project <name>`.

## Configuration

The variables use the prefix `MS_KIT_` (microservice kit).

| Variable | Default | Meaning |
|---|---|---|
| `MS_KIT_ENV_FILE` | `~/.ms-kit/local.env` | The developer env file that `run-local.sh` loads |
| `MS_KIT_JDK` | `21` | The JDK version the build pins |

`service.env` keys: [`scripts/README.md`](scripts/README.md#serviceenv).

## Requirements and limits

- bash 3.2+ (stock macOS), `find`, `grep`, `sed`, `awk`, `lsof`; Maven; [hurl](https://hurl.dev)
  8.x for the acceptance suites.
- JDK selection uses `/usr/libexec/java_home`, so it is macOS-only today.
- The scripts assume a multi-module Maven reactor with one `*-container` module that starts the
  application, an optional Helm chart, and strict `MAJOR.MINOR.PATCH` versions. A service that
  does not fit records the gap in its own `AGENTS.md`; extend a script when real work needs it.
